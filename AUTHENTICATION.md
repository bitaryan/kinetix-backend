# GPSS FastAPI Authentication

This implementation uses a short-lived signed JWT access token and a rotating opaque refresh token. The refresh token is returned only in an `HttpOnly` cookie; PostgreSQL stores its SHA-256 hash, never the token itself. Passwords use Argon2 through `pwdlib` and are never returned or logged.

## What is included

- JSON login at `POST /api/v1/auth/login`, accepting `userId`, `password`, and `role`.
- `POST /api/v1/auth/refresh`, which validates an unrevoked server-side session and rotates the cookie token.
- `POST /api/v1/auth/logout` and `POST /api/v1/auth/logout-all` to revoke sessions.
- `GET /api/v1/auth/me`, protected by FastAPI's HTTP Bearer security integration.
- `POST /api/v1/auth/users`, restricted to `ADMIN`, for provisioning workforce accounts.
- RBAC roles: `ADMIN`, `MANAGER`, and `EMPLOYEE`.
- Account lockout after five incorrect password checks for 15 minutes.
- Consistent JSON success/error envelopes, including validation and authorization errors.

Every protected request verifies its JWT, user activity, session ownership, session expiration, and revocation state. Logging out invalidates its access token immediately, not only after its normal 15-minute expiration.

## PostgreSQL database schema

Alembic migration `20260808_0001` creates these PostgreSQL objects through SQLAlchemy/Alembic operations:

| Object | Purpose |
| --- | --- |
| `user_role` enum | `ADMIN`, `MANAGER`, and `EMPLOYEE` role values. |
| `users` | Workforce identity, Argon2 password hash, account status, failed-attempt count, lock state, and timestamps. |
| `active_sessions` | Hashed rotating refresh token, device metadata, expiration, revocation state, and a cascading foreign key to `users`. |

`users.user_id` and `active_sessions.session_id` are UUID primary keys generated by the ORM. The employee-facing identifier is `users.employee_id` (for example `EMP1001`), which is unique and is sent as `userId` by the mobile client. PostgreSQL supplies lookup indexes through the unique constraints on employee ID, email, and refresh-token hash; the migration also adds an index on `active_sessions.user_id`.

## Create the database and schema

1. Copy the sample environment file and generate a signing key:

   ```bash
   cp .env.example .env
   openssl rand -hex 32
   ```

   Put that generated value in `JWT_SECRET_KEY`. Set `DATABASE_URL` to your PostgreSQL server, for example:

   ```text
   postgresql+asyncpg://gpss:your-password@localhost:5432/gpss
   ```

2. Start PostgreSQL. For local development, the supplied Docker definition creates the `gpss` database and user:

   ```bash
   docker compose up -d postgres
   ```

   Alternatively, create the role and database with PostgreSQL's administrative utilities (not application code):

   ```bash
   createuser -U postgres --pwprompt gpss
   createdb -U postgres -O gpss gpss
   ```

3. Install the backend dependencies and apply the versioned schema migration:

   ```bash
   python3 -m venv .venv
   source .venv/bin/activate
   python -m pip install -e '.[dev]'
   alembic upgrade head
   ```

   `alembic upgrade head` is the schema-creation step. It is repeatable: Alembic records revision `20260808_0001` in `alembic_version` and will not recreate applied tables.

4. Create the first administrator without exposing their password in shell history:

   ```bash
   python -m app.scripts.create_admin
   ```

5. Run the API:

   ```bash
   uvicorn app.main:app --reload
   ```

   Visit `http://127.0.0.1:8000/docs` to inspect protected endpoints and paste a bearer token into the authorization dialog.

## Example login request

```http
POST /api/v1/auth/login
Content-Type: application/json

{
  "userId": "EMP1001",
  "password": "a-long-unique-password",
  "role": "EMPLOYEE"
}
```

The access token is in `data.accessToken`; the browser/client cookie jar receives the `refresh_token` cookie. Use `Authorization: Bearer <data.accessToken>` for protected calls.

## Production checklist

- Serve the API over HTTPS and set `COOKIE_SECURE=true`.
- Set `APP_ENV=production` (enforces secure cookies and https CORS origins).
- Set an explicit, trusted `BACKEND_CORS_ORIGINS` list; do not use `*` when cookies are enabled.
- Use a long, unique `JWT_SECRET_KEY` from a secret manager and rotate it through a controlled deployment.
- Keep `LOGIN_RATE_LIMIT_PER_MINUTE` / `REFRESH_RATE_LIMIT_PER_MINUTE` enabled; put a WAF in front as well.
- Configure `TRUSTED_PROXY_IPS` before relying on `X-Forwarded-For` for client IP.
- Run every schema change as a reviewed Alembic migration; do not alter these tables manually.
- Administrator accounts are created only via `python -m app.scripts.create_admin`, not `POST /auth/users`.

## FastAPI guidance used

The structure follows FastAPI's documented JWT pattern: a signed bearer access token is decoded by a dependency, and a password hash is stored instead of the password. It uses a database ORM/session per request, as shown in FastAPI's SQL database guide. FastAPI's scope guide notes that scopes are optional and must still be enforced in application code; this project uses the requested three-role RBAC policy instead. See [FastAPI: OAuth2 with JWT](https://fastapi.tiangolo.com/tutorial/security/oauth2-jwt/), [FastAPI: SQL databases](https://fastapi.tiangolo.com/tutorial/sql-databases/), and [FastAPI: OAuth2 scopes](https://fastapi.tiangolo.com/advanced/security/oauth2-scopes/).
